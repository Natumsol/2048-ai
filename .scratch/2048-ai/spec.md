# 2048 AI Web 游戏

Status: ready-for-agent

## Problem Statement

用户需要一个可在桌面和移动浏览器中直接游玩的 2048 游戏。游戏不仅要有流畅、响应式的 PixiJS 画面，还要让用户能够在任意当前局面把控制权交给神经网络策略模型，观察 AI 连续完成对局，并随时暂停后恢复人工操作。

项目还需要一条可信、可复现的离线训练链路。训练得到的模型必须能在浏览器本地运行，不能依赖后端推理，也不能用运行时搜索或手写启发式伪装成神经网络决策。原先设想的 Keras.js 与当前模型格式之间存在兼容和维护风险，因此需要采用维护中的训练、交换和 Web 推理技术，同时用明确的模型契约、跨语言规则一致性和可量化的 AI 基准证明交付质量。

## Solution

交付一个使用 PixiJS v8 绘制棋盘与动画的纯客户端 Web 游戏。用户可以通过键盘或触摸完成经典 4×4 2048 对局，查看分数与最高分，重新开始，刷新后恢复当前对局，并在任意局面启动或暂停自动游玩。

游戏规则由一个与渲染无关、可注入确定性随机数源的 TypeScript 引擎统一负责。PixiJS 只消费移动、合并和生成事件来表现画面，HTML/CSS 负责语义化控件、状态与无障碍信息。应用先提供人工游戏，再于后台加载 ONNX 策略模型；WebGPU 可用时用于推理，否则回退到单线程 WASM。模型失败时只禁用自动游玩，不影响人工对局。

离线训练使用 PyTorch。确定性的 Expectimax 教师以经典规则和手写叶节点启发式生成四方向软目标，数据同时覆盖教师正常轨迹和受扰动后的恢复局面。小型残差 CNN 学习教师策略，导出为固定契约的 FP32 ONNX 模型。最终交付的模型必须使用 TypeScript 权威规则引擎完成 1,000 个固定种子的 AI 基准，并达到既定胜率与最大方块指标。

## User Stories

1. 作为桌面玩家，我希望使用方向键移动方块，以便自然地进行对局。
2. 作为桌面玩家，我希望也能使用 WASD 移动方块，以便使用自己习惯的键位。
3. 作为移动端玩家，我希望在棋盘上滑动来选择方向，以便不依赖屏幕键盘。
4. 作为移动端玩家，我希望棋盘手势只在明确滑动时阻止页面滚动，以便仍能正常浏览页面。
5. 作为窄屏设备用户，我希望在 320 CSS px 宽的视口中仍能看到完整棋盘和控制区，以便在小屏幕上游玩。
6. 作为横屏设备用户，我希望布局适应横向空间，以便所有控件保持可访问。
7. 作为玩家，我希望开局随机出现两个方块，以便遵循经典 2048 规则。
8. 作为玩家，我希望每次合法移动后按 90%/10% 的概率生成 `2` 或 `4`，以便游戏行为符合经典规则。
9. 作为玩家，我希望一次移动中的每个方块最多合并一次，以便连锁合并结果正确。
10. 作为玩家，我希望无效方向不改变棋盘、不增加分数且不生成新方块，以便规则可预测。
11. 作为玩家，我希望看到当前分数，以便了解本次对局表现。
12. 作为回访玩家，我希望看到保存在当前浏览器中的最高分，以便与自己的历史表现比较。
13. 作为玩家，我希望重新开始时清空当前分数但保留最高分，以便开启新对局而不丢失纪录。
14. 作为正在游玩的玩家，我希望误触重新开始时先得到确认，以免丢失当前对局。
15. 作为尚未移动或已经游戏结束的玩家，我希望重新开始无需多余确认，以便快速进入新对局。
16. 作为玩家，我希望首次出现 2048 时看到庆祝提示，以便感知达成目标。
17. 作为希望挑战更高方块的玩家，我希望 2048 提示不阻断对局，以便继续游玩。
18. 作为玩家，我希望只有在不存在合法移动时才进入游戏结束，以便规则语义明确。
19. 作为游戏结束的玩家，我希望看到分数、最大方块和移动次数，以便回顾本次结果。
20. 作为游戏结束的玩家，我希望系统等待我明确重新开始，而不是自动开启下一局，以便我有时间查看结果。
21. 作为快速输入的玩家，我希望动画期间最多保留我的最新一个方向，以便操作不会被完全吞掉，也不会积压旧指令。
22. 作为玩家，我希望移动、合并和新方块出现有短促、清晰的动画，以便理解棋盘变化。
23. 作为偏好减少动态效果的用户，我希望游戏尊重系统设置并允许减少动画，以便舒适使用。
24. 作为返回页面的玩家，我希望刷新后恢复棋盘、分数、移动次数和随机数状态，以便继续同一对局。
25. 作为返回页面的玩家，我希望刷新后 AI 保持暂停，以免页面打开后未经操作就继续走棋。
26. 作为玩家，我希望可以从任意当前局面启动自动游玩，以便把已经进行的对局交给 AI。
27. 作为观察 AI 的用户，我希望 AI 连续选择合法移动，直到我暂停或游戏结束，以便完整观察策略表现。
28. 作为玩家，我希望暂停 AI 后保留当前局面，以便恢复人工操作或稍后继续自动游玩。
29. 作为玩家，我希望人工输入与 AI 不会同时控制棋盘，以免产生竞态和意外移动。
30. 作为观察者，我希望选择慢速、标准或快速自动游玩，以便在细看决策和快速跑局之间切换。
31. 作为观察者，我希望自动游玩等待上一步动画完成后再决策，以便画面与真实状态保持一致。
32. 作为观察者，我希望运行中可以切换自动游玩速度，以便无需中断对局。
33. 作为观察者，我希望看到模型的加载、就绪、运行、暂停和失败状态，以便理解当前是否由 AI 控制。
34. 作为技术用户，我希望看到当前使用 WebGPU 还是 WASM 推理，以便了解运行环境。
35. 作为观察者，我希望看到 AI 最近选择的方向，以便跟随策略行为。
36. 作为观察者，我不希望看到未经校准的伪「置信度」，以免把 logits 误解为可靠概率。
37. 作为人工玩家，我希望模型仍在后台加载时即可开始对局，以便 AI 资源不阻塞游戏启动。
38. 作为模型加载失败的用户，我希望人工游戏仍然可玩，并能看到错误和重试入口，以便不因 AI 故障失去核心功能。
39. 作为玩家，我希望 AI 输出异常时自动游玩安全暂停，而不是悄悄改用随机移动，以便问题不会被隐藏。
40. 作为玩家，我希望模型异常后当前棋盘仍可人工继续，以便保留对局进度。
41. 作为键盘用户，我希望所有控制按钮都有可见焦点和原生键盘行为，以便不依赖鼠标。
42. 作为屏幕阅读器用户，我希望获得可读的 4×4 棋盘、分数、AI 状态和游戏结束提示，以便理解并控制对局。
43. 作为色觉差异用户，我希望方块始终显示清晰数字且具有足够文字对比度，以便不只依赖颜色识别数值。
44. 作为隐私敏感用户，我希望分数、存档和设置只保存在本地，且游戏不包含分析、广告或追踪，以便不上传我的行为。
45. 作为普通用户，我希望打开静态网站即可使用默认模型，以便不安装 Python、不上传模型也不连接推理服务器。
46. 作为弱兼容环境用户，我希望 WebGPU 不可用时自动回退到 WASM，以便仍能使用自动游玩。
47. 作为不支持 AI 推理后端的用户，我希望得到清晰说明且仍能人工游玩，以便应用能够优雅降级。
48. 作为开发者，我希望游戏规则独立于 PixiJS、DOM 和真实时钟，以便确定性测试和复用。
49. 作为开发者，我希望一次移动返回状态和可观察事件，以便动画无需重复推导规则。
50. 作为开发者，我希望固定种子能重放相同对局，以便复现缺陷并比较模型。
51. 作为开发者，我希望 TypeScript 规则引擎是最终权威，以便浏览器行为决定产品正确性。
52. 作为训练工程师，我希望 Python 环境通过共享一致性用例与 TypeScript 对齐，以便高速模拟不会产生规则漂移。
53. 作为训练工程师，我希望 Expectimax 对相同局面产生确定的四方向软目标，以便数据可复现。
54. 作为训练工程师，我希望训练集包含受扰动后的较差局面，以便 AI 能从人工形成的非典型局面恢复。

59. 作为训练工程师，我希望通过 `full` 配置生成正式模型，以便交付物来自完整数据预算。

## Implementation Decisions

- 游戏采用经典 4×4 2048 规则：开局两个方块；每次合法移动后在随机空格生成一个方块，其中 `2` 的概率为 90%、`4` 为 10%；一个方块在单次移动中最多参与一次合并。
- 分数等于对局中所有合并所产生的新方块数值之和。最高分由当前浏览器持久化，人工操作和自动游玩共享计分语义。
- 首次出现 2048 触发一次非阻塞提示但不结束对局。没有任何合法移动才进入游戏结束。
- 重新开始在进行中的非空对局上需要确认；确认界面临时暂停自动游玩，取消后恢复此前控制状态。
- 当前对局持久化棋盘、分数、移动次数、完整 PRNG 状态和 2048 提示状态。刷新后恢复同一对局，但自动游玩始终以暂停状态恢复。
- 自动游玩提供慢速约 600 ms、标准约 250 ms 和快速约 80 ms 三档，标准档为默认值。每一步等待上一步动画完成，再读取最新棋盘并推理。
- 人工输入在动画期间最多缓存一个方向，新输入替换旧缓存。自动游玩不缓存决策。
- UI 使用简体中文，用户可见文案集中管理，为未来国际化保留边界，但首版不提供语言切换。
- 视觉采用受经典 2048 启发的暖色、中性色风格，但不做像素级复刻。棋盘、方块和文字由 PixiJS 矢量能力绘制，不依赖图片素材。
- Web 工程采用 Vite、strict TypeScript 和 PixiJS v8。PixiJS 负责棋盘及动画，语义化 HTML/CSS 负责标题、分数、按钮、选择器、状态和无障碍信息。不引入 React、Vue 等 UI 框架。
- 应用级「对局控制器」是主要产品 seam。它以命令驱动一局游戏，协调规则、控制权、动画完成、模型决策、存档和错误状态，并返回可观察快照和事件。
- 规则引擎不依赖 PixiJS、DOM、存储或真实时钟。它接受可注入 PRNG，并返回移动后的状态以及移动、合并、生成事件。
- TypeScript 规则引擎是规则权威。Python 可实现用于教师搜索和批量数据生成的等价环境，但必须通过共享 JSON 一致性语料。
- TypeScript 与 Python 共同实现 `xoshiro128**` 32 位 PRNG。普通新对局由浏览器安全随机源生成种子；存档保存完整状态；测试和基准使用固定种子。
- 应用是无后端的纯客户端静态网站。游戏、存档、模型加载和推理均在浏览器完成，不包含账号、排行榜或远程推理 API。
- 页面先进入人工可玩状态，再后台加载模型。自动游玩按钮呈现加载、就绪、运行、暂停和失败状态；失败提供重试且不阻断人工游戏。
- PixiJS 以 WebGL 为兼容基线。ONNX Runtime Web 按 WebGPU、WASM 的顺序尝试推理后端；WASM 不要求 COOP/COEP，允许单线程运行。
- 如果推理抛错、输出形状错误、包含非有限值或无法选择合法移动，自动游玩立即暂停并公开错误。不得隐藏回退到随机、Expectimax 或手写策略。
- 策略模型只读取当前棋盘，不读取分数、移动历史、教师启发式或未来随机结果。运行时不执行树搜索。
- 模型输入为 `float32[1,16,4,4]` one-hot 张量：通道 0 表示空格，通道 1–14 表示 `2¹` 到 `2¹⁴`，通道 15 表示 `2¹⁵` 及以上。
- 模型输出为 `float32[1,4]` 方向 logits，固定顺序为 `[上, 右, 下, 左]`。Web 端先屏蔽非法移动，再选择最高剩余 logit。
- 模型采用约 2 MB 的小型残差 CNN：64 通道卷积主干、少量保持棋盘尺寸的残差块和输出四方向 logits 的小型全连接头。只使用 ONNX Web 后端支持成熟的基础算子。
- 模型由 PyTorch 训练并以固定形状、FP32、ONNX opset 18 导出。输入名为 `board`，输出名为 `logits`。首版不量化。
- 模型元数据使用独立 `contractVersion`，首版为 `1`，并记录输入输出名称、形状、训练配置、数据配置、随机种子、基准指标和模型 SHA-256。
- 浏览器加载前验证模型清单、契约和内容哈希。不兼容或损坏的模型不能启用自动游玩。
- Expectimax 仅作为离线教师。机会节点按真实空位以及 `2/4` 概率精确计算，不读取未来随机结果，不使用随机机会采样或墙钟超时。
- 教师允许使用空格数量、单调性、相邻平滑度、可合并数量和最大方块角落偏好等叶节点启发式。搜索使用确定性固定深度或固定节点预算与确定性置换表。
- 教师对所有合法方向输出评估值，经温度归一化形成软目标；非法方向的目标概率为 0。学生通过软目标损失学习方向排序。
- 正式数据包含约 250,000 个未扩增局面，正常教师轨迹与受扰动恢复轨迹各约一半。受扰动仅执行合法的非首选方向，后续局面重新由教师标注。
- 数据按完整对局种子切分为 80% 训练、10% 验证、10% 测试。八种旋转与镜像对称只在训练时动态应用，验证和测试不扩增。
- 数据在磁盘上保存紧凑的方块指数、合法掩码、教师软目标、种子、步数和来源，不保存展开后的 one-hot 副本。数据集附带配置与哈希。
- 训练提供 `smoke` 与 `full` 配置。`smoke` 在几分钟内验证端到端链路；`full` 使用正式预算并产出默认模型。缓存和中间产物总占用控制在 5 GB 内。
- 每个 epoch 评估验证集软目标损失并运行 100 个固定种子的快速完整对局，以游戏表现为主选择 checkpoint。测试集只用于最终候选。
- 教师在正式数据生成前必须在 1,000 个固定种子中至少 90% 达到 2048，最大方块中位数不低于 2048。
- 最终 ONNX 模型必须通过 AI 基准：1,000 个固定种子中不执行非法移动，至少 50% 达到 2048，最大方块中位数不低于 1024。
- PyTorch 与 ONNX 对固定棋盘语料的 logits 误差不得超过 `1e-5`，经过合法移动屏蔽后的最终方向必须完全相同。
- 最终 AI 基准必须使用导出的 ONNX 模型和 TypeScript 权威引擎，而不是 PyTorch checkpoint 或 Python 环境。
- 训练自动选择 CUDA、Apple MPS 或 CPU；教师数据生成支持 CPU 多进程。正式导出与最终基准固定在 CPU 路径上执行。
- Web 端固定 Node 22 与 npm 并提交锁文件；训练端由 `uv` 管理，固定 Python 3.12 并提交 Python 项目与依赖锁定信息。
- 代码按规则引擎、渲染、AI、UI、训练教师、Python 环境、模型、训练脚本、共享一致性语料和浏览器端到端测试等职责组织，但保持单一项目而非多个独立发布包。
- Web 端使用 TypeScript strict、ESLint 和 Prettier；Python 使用 Ruff、Pyright 与 pytest。日常统一检查不包含完整数据生成、完整训练或 1,000 局基准。
- 自动游玩预热后的「编码、WASM 推理、合法移动选择」p95 目标不超过 50 ms。动画以 60 FPS 为目标，人工输入不等待模型，任何时刻不并发运行两次推理。
- 无障碍包括原生可聚焦控件、减少动态效果、适度 ARIA live 状态，以及与 Canvas 同步的屏幕阅读器可读 4×4 文本棋盘。
- 本地持久化仅包含当前对局、最高分和用户设置。应用不包含分析、广告、崩溃上报或其他第三方追踪。
- 实现开始时初始化本地 Git 仓库，以 `main` 为默认分支并完善忽略规则；不创建远程仓库或绑定托管平台。
- 交付通过生产构建生成普通静态资源。首版不执行线上发布，也不要求 PWA 或 Service Worker。

## Testing Decisions

- 好测试只观察公开命令、状态快照、领域事件、模型产物和最终浏览器行为，不断言私有函数、内部数据结构、PixiJS 节点层级或逐帧实现细节。
- 主要产品测试 seam 是无界面的「对局控制器」。依赖使用可控 PRNG、策略模型、时钟、存储和动画完成信号替代，从最高层验证新对局、人工移动、自动游玩、暂停、速度切换、重开确认、存档恢复、获胜提示、游戏结束和模型错误。
- 第二个主要 seam 是「策略模型产物」。固定棋盘语料贯穿 PyTorch、ONNX 导出、Python ONNX Runtime 和 TypeScript ONNX 适配器，验证契约、哈希、数值容差、合法移动屏蔽和最终方向。
- TypeScript 规则引擎使用示例测试和属性测试。属性覆盖方块总值只因生成而增加、合并得分正确、一次移动不重复合并、无效移动不生成方块、合法移动判定和固定种子可重放。
- TypeScript 与 Python 环境共同消费共享 JSON 一致性语料，覆盖四个方向、复杂合并、空棋盘边界、生成概率映射、PRNG 状态和固定种子完整轨迹摘要。
- Python 测试覆盖教师机会节点概率、搜索确定性、软目标合法性、扰动轨迹、按种子切分、防数据泄漏、对称变换的棋盘与方向映射、紧凑数据编解码和训练 smoke 流程。
- 导出测试验证 ONNX checker、固定输入输出名称与形状、opset、有限 logits、PyTorch/ONNX 数值等价以及模型清单与文件哈希。
- 模型选择使用验证损失和 100 种子快速对局；教师与最终模型分别使用独立的正式 1,000 种子质量门槛。
- Playwright 只覆盖真实浏览器连线：方向键、WASD、滑动、输入缓存、重新开始确认、响应式布局、存档恢复、减少动态效果、模型后台加载、WebGPU/WASM 状态、自动游玩启动与暂停、错误降级和游戏结束。
- 浏览器层不重复穷举规则组合；规则正确性在「对局控制器」和纯引擎 seam 完成。动画测试断言开始、完成和最终视觉状态，不维护脆弱的逐帧截图。
- 性能测试在模型预热后统计编码、单线程 WASM 推理和方向选择的 p95，并验证自动游玩不会重入推理。人工交互测试验证模型工作不会阻塞人工输入。
- 当前代码库为绿地项目，没有可复用的既有测试先例；上述两个主要 seam 是项目建立后的测试先例，后续功能应优先复用，而不是增加新的横切 seam。

## Out of Scope

- Keras、Keras.js 及其模型格式。
- 账号、排行榜、云同步、后端 API 和多人模式。
- 撤销。
- 背景音乐、音效、静音和音量设置。
- PWA、Service Worker、离线安装承诺。
- 线上托管与发布。
- 浏览器内训练或在线调参。
- 用户上传本地模型、输入远程模型 URL 或选择其他模型。
- 自定义棋盘尺寸、主题系统、关卡和挑战模式。
- 运行时 Expectimax、树搜索或手写策略回退。
- 模型量化。
- 英文或其他语言界面及语言切换器。
- 分析、广告、崩溃上报和用户追踪。
- 外部玩家对局采集与基于玩家数据的持续训练。

## Further Notes

- Expectimax 的最终深度或节点预算、启发式权重、软目标温度、优化器超参数和精确网络参数属于实验确定项，不是未解决的产品决策。它们必须记录在模型与数据清单中，并受教师门槛、AI 基准、2 MB 目标体积和 Web 性能门槛约束。
- 当前开发机可运行 CPU 训练，但没有 CUDA 或 Apple MPS，完整数据生成和训练可能持续数小时。`smoke` 流程必须先证明全链路可用，再启动 `full` 流程。
- 当前磁盘空间有限；生成器、缓存和 checkpoint 必须支持增量写入、清理与恢复，不能假设无限临时空间。
- 已接受的架构决定包括：使用 PyTorch 与 ONNX Runtime Web、固定跨语言策略模型契约，以及以 TypeScript 游戏引擎作为规则权威。实现不得在没有新决策记录的情况下绕过这些边界。
- 默认模型是首版完整交付的一部分。只有训练脚本、占位模型或未通过 AI 基准的 smoke 模型不构成规格完成。
